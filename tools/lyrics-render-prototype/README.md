# 歌词连续绘制原型（临时实验）

问题：在相同排版与时间轴下，QML 双层裁切和 C++ 缓存绘制，哪条路径更适合词典笔？

这是 P0 绘制实验，不是正式歌词组件；不读取歌曲、不改变配置、不注入触摸、不重启宿主应用。
A/B 使用同一 QTextLayout 视觉行、grapheme 边界与合成时间轴。每个 grapheme 的时长相等，
用于观察连续扫色，不代表实际逐字歌词的节奏；真实词起止时间与音频时钟属于 P1。

## 运行

依赖：现有 Zig、ARM64 Qt 5.15.2、主机 moc、ADB。产物在 `build/lyrics-render-prototype/`。

构建并执行设备离屏测量（默认，不接管设备界面）：

```sh
python3 tools/lyrics-render-prototype/run.py
```

只构建：

```sh
python3 tools/lyrics-render-prototype/run.py --build-only
```

维护者手动启动可见对比窗口：

```sh
python3 tools/lyrics-render-prototype/run.py --launch
```

窗口为 320×170，底部按钮为 A/B 切换、换样例、暂停/继续和归零。右上角 × 或 Escape 退出。
有界面的启动仅由维护者执行；代理不执行 `--launch` 或触摸注入。
可见窗口使用设备默认 Qt Quick 后端；离屏测量明确使用 `QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software`。

## 实现与样例

- A：每个视觉行一层底色 Text；12 个预分配裁切槽绘制高亮 Text，逐帧只修改范围，不重建整段富文本。
- B：QTextLayout 将一段文字排成两张缓存图片；scene graph 底层文字节点加高亮片段节点。逐帧更新片段矩形和纹理 UV，排版变更时才重建纹理。
- 两者共用视觉范围计算，先按 grapheme 分段，再按视觉行合并相邻高亮范围。支持本组样例的 RTL 反向推进。
- C++ 排版/图片也存在于 A 的公共测量夹具中。总 RSS 不是正式组件增量内存，不能拿来直接推断正式播放器内存。
- 固定五组：中文、英文跨行、中英混排/组合字符/家庭 emoji、中文长句、多语言/连字/双向文本。
- 自动采样前 1 秒预热，之后记录帧交换间隔及进程 user+system CPU 时间。采样结束后冻结到 50% 进度，保存五组截图。
- 帧间隔是窗口帧交换事件的到达间隔，不是独立 GPU 绘制耗时，更不是物理屏幕刷新率。

## 已测结果

在当前 ADB 词典笔上以软件离屏模式运行，宿主应用继续运行。末次完整测量：

| 指标 | A：QML | B：C++ 缓存 |
| --- | ---: | ---: |
| 采样帧数 | 580 | 604 |
| 帧交换间隔中位数 | 16.06 ms | 15.97 ms |
| 帧交换间隔 P95 | 21.15 ms | 17.18 ms |
| 预热后约 10 秒累计 CPU | 3847 ms | 1550 ms |
| 进程 RSS | 38960 KiB | 37428 KiB |
| 进程峰值 RSS | 39600 KiB | 37428 KiB |

前一轮同样观察到 C++ CPU 消耗更低（1559 ms 对 3680 ms），趋势一致，但这不是统计充分的多轮性能研究。
本组最大的两张文字图片合计 178176 字节，约 174 KiB；尚不包括 scene graph 纹理副本、字体缓存和其他 Qt 开销。

每轮原始日志、`results.json` 和 `qml-0.png`…`qml-4.png` / `native-0.png`…`native-4.png` 都保存在构建目录。
当前构建目录还有 `comparison.png`，左 A 右 B，上下对应五组样例。

## 判断与未完成的验证

**优先选 B 作为正式实现候选**：连续裁切画面接近，软件路径的 CPU 消耗明显更低，帧间隔尾部更短。
正式实现需重新整理成可维护组件，不能直接将此原型移进生产目录。

已通过：交叉编译、设备离屏运行、五组截图、连续高亮跨行观察；日志无 QML 类型/绑定错误。
两条路径仍有轻微光栅化差异；不能以截图接近宣称所有文字排版均正确。

待维护者手动验证：

1. `--launch` 后分别观察 A/B 的连续扫色、暂停和换样例；确认实际 Wayland 后端下没有纹理错位或闪烁。
2. 样例 2/4 的跨行边界、样例 3 的组合字符，以及样例 5 的阿拉伯文方向。
3. 当前字体将家庭 ZWJ emoji 显示为独立家庭成员，两种路径一致；grapheme 数据保持一个组合，但字体不能合成图形。这需在正式字体策略中记录/处理。

本实验未测宿主 `currentPos` 的通知周期，也未接入音频、译文、滚动或生产页面。
宿主位置通知间隔/抖动仍需在用户播放歌曲时采样，不能用本实验的 16 ms 合成刷新间隔代替。
可见 Wayland/GPU 验证与宿主时钟基线完成后，才能关闭整个 P0 并进入 P1。
